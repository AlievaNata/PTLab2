# Лабораторная работа № 2 по дисциплине «Технологии программирования»

**Тема:** изучение фреймворка MVC. **Вариант 2:** магазин мягкой мебели.

## 1. Постановка задачи

### Цели работы

1. Познакомиться с моделью MVC, её сущностью и основными фреймворками на её основе.
2. Разобраться с сущностями «модель», «контроллер», «представление» и их функциональным назначением.
3. Получить навыки разработки веб-приложений с использованием MVC-фреймворков и написания модульных тестов к ним.

### Индивидуальное задание (вариант 2)

Доработать учебный проект интернет-магазина (Django), добавив новую функциональность и информацию в базу данных в соответствии с типом магазина, составить модульные тесты и по возможности покрыть тестами максимальный объём кода.

| Тип магазина | Функциональность приложения |
|---|---|
| Магазин мягкой мебели | Покупатель может положить товары в корзину, общая стоимость которой показывается пользователю. Корзина может содержать только один экземпляр одного товара. |

## 2. Краткое описание проекта

Исходный проект — простейший магазин на Django: список товаров и форма покупки одного товара. В ходе работы он превращён в магазин мягкой мебели с корзиной.

### Что добавлено

* **Данные магазина.** Категории (диваны, кресла, пуфы и банкетки, кушетки) и 12 товаров с описаниями и ценами в рублях — файл `shop/fixtures/products.yaml`.
* **Каталог** с фильтром по категории: `/` и `/?category=<id>`.
* **Корзина** (`/cart/`):
  * добавление и удаление товаров, очистка корзины;
  * общая стоимость и количество товаров показываются на странице корзины и в шапке каждой страницы;
  * в корзине не может быть двух экземпляров одного товара: повторное нажатие «В корзину» ничего не добавляет и выводит пользователю сообщение;
  * корзина привязана к сессии, поэтому регистрация покупателя не нужна.
* **Админка** (`/admin/`): все модели зарегистрированы, товары корзины редактируются прямо в карточке корзины.
* Покупка отдельного товара «сразу» (`/buy/<id>/`) из исходного проекта сохранена.

### Соответствие модели MVC

| Компонент MVC | Где в проекте | Что делает |
|---|---|---|
| **Модель** | `shop/models.py` | `Category`, `Product`, `Purchase`, `Cart`, `CartItem`; вся бизнес-логика корзины (`Cart.add`, `remove`, `clear`, `summary`, `total_price`) |
| **Представление** | `shop/templates/shop/*.html` | `base.html`, `index.html`, `cart.html`, `purchase_form.html` — только отображение данных |
| **Контроллер** | `shop/views.py`, `shop/urls.py`, `shop/cart.py` | разбор запроса, обращение к модели, выбор шаблона или перенаправление |

Django называет эту схему MTV (Model-Template-View): его «View» играет роль контроллера, а «Template» — представления.

### Модель данных

```
Category 1 ──< Product 1 ──< CartItem >── 1 Cart
                  1
                  └──< Purchase
```

* `Product.category` необязателен (`SET_NULL`): удаление категории не удаляет товары.
* `CartItem` имеет ограничение `UniqueConstraint(cart, product)`. Требование «один экземпляр одного товара» выполняется и в коде (`Cart.add` возвращает `False` при повторном добавлении), и на уровне СУБД, поэтому его нельзя обойти даже при одновременных запросах.

### Адреса

| URL | Метод | Действие |
|---|---|---|
| `/` | GET | каталог |
| `/cart/` | GET | содержимое корзины и итоговая стоимость |
| `/cart/add/<id>/` | POST | положить товар в корзину |
| `/cart/remove/<id>/` | POST | убрать товар из корзины |
| `/cart/clear/` | POST | очистить корзину |
| `/buy/<id>/` | GET, POST | покупка товара «сразу» |
| `/admin/` | | административный интерфейс |

Изменяющие запросы принимаются только методом POST и защищены CSRF-токеном.

## 3. Используемые языки, библиотеки и технологии

* **Python 3** — язык программирования.
* **Django** — MVC/MTV-фреймворк (ORM, миграции, шаблоны, сессии, админка, тестовый клиент).
* **PostgreSQL** — СУБД; драйвер **psycopg2**.
* **PyYAML** — загрузка данных из фикстуры `products.yaml`.
* **HTML + шаблонизатор Django** — представления.
* **unittest / `django.test.TestCase`** — модульные тесты; **coverage** — измерение покрытия.
* Из исходного проекта остались `dj-database-url`, `django-heroku`, `whitenoise`, `gunicorn` (настройки развёртывания). В этой работе они не используются: CI/CD и развёртывание в задание не входили.

## 4. Запуск проекта

```
pip install -r requirements.txt
```

Создайте базу и укажите пароль пользователя `postgres` в переменной окружения `DATABASE_PASSWORD` (её читает `tplab2/settings.py`; параметры подключения: база `django_db`, пользователь `postgres`, `localhost:5432`):

```
postgres=# create database django_db owner postgres;
```

```
python manage.py migrate
python manage.py loaddata products.yaml
python manage.py runserver
```

Приложение откроется по адресу http://localhost:8000.

## 5. Тестирование

```
python manage.py test shop/tests/
```

Django создаёт для тестов отдельную базу `test_django_db` и удаляет её по окончании, поэтому у пользователя PostgreSQL должно быть право `CREATEDB`.

Покрытие кода:

```
pip install coverage
coverage run manage.py test shop/tests/
coverage report
```

В проекте 90 тестов:

| Файл | Тестов | Что проверяется |
|---|---|---|
| `test_models.py` | 31 | модели; логика корзины: добавление, повторное добавление, удаление, очистка, подсчёт стоимости; ограничение уникальности на уровне БД; каскадное удаление |
| `test_views.py` | 37 | каталог и фильтр по категории; добавление, удаление и очистка корзины; страница корзины и итоговая стоимость; покупка «сразу»; ответ 404 для несуществующего товара, 405 для GET, 403 без CSRF-токена; защита от небезопасного перенаправления `next` |
| `test_cart_helper.py` | 7 | получение корзины из сессии: нет корзины, создание, устаревший идентификатор |
| `test_context_processors.py` | 5 | счётчик и сумма корзины в шапке всех страниц |
| `test_fixtures.py` | 6 | загрузка категорий и товаров, повторная загрузка без дублей |
| `test_admin.py` | 3 | регистрация моделей в админке, методы `CartAdmin` |
| `test_migrations.py` | 1 | модели и миграции не расходятся (аналог `makemigrations --check`) |

В тестах на уникальность ошибка `IntegrityError` обёрнута в `transaction.atomic()`. Это нужно именно для PostgreSQL: после такой ошибки транзакция теста иначе остаётся в аварийном состоянии.

## 6. Выводы

* Модель MVC разделяет приложение на данные и правила работы с ними (модели), отображение (шаблоны) и обработку запросов (контроллеры). Благодаря этому правило «один экземпляр товара в корзине» реализовано один раз в модели и ограничении БД, а представления и контроллеры лишь пользуются им. Шаблоны не содержат бизнес-логики, а логику корзины можно тестировать без HTTP-запросов.
* Для фреймворка Django характерна терминология MTV: его «View» соответствует контроллеру MVC, а «Template» — представлению.
* Корзину удобно привязывать к сессии: покупателю не нужна регистрация, а в базе нет лишних данных. Чтобы просмотр каталога не создавал пустые корзины, корзина создаётся только при первом добавлении товара.
* Ограничение уникальности в СУБД надёжнее проверки только в коде: оно работает и при параллельных запросах. Поэтому `Cart.add` использует `get_or_create`, а в тестах проверяется как логика приложения, так и отказ самой базы данных.
* Раздельные модульные тесты на модели, контроллеры, вспомогательный код, фикстуры и админку позволяют быстро локализовать ошибку. Тест синхронности моделей и миграций страхует от забытых миграций.
* Работа с PostgreSQL имеет свои особенности (права `CREATEDB` для тестовой базы, поведение транзакции после ошибки целостности), которые нужно учитывать при написании тестов.
